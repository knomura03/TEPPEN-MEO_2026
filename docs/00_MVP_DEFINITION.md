# TEPPEN MEO：MVP定義（モック脱却）

最終更新: 2026-02-03

## 目的（モック脱却の定義）
TEPPEN MEOを「画面があるだけのモック」から、**実ユーザーがログインし、実データが保存され、最小限の外部連携（GBP）が動く**状態へ移行します。

あわせて、knomura（ADMIN）の作業・判断を最小化し、**原則として管理画面（GUI）で運用できる**形に寄せます。

## 前提（決定事項）
- バックエンド: **Supabase**
- MVPで最優先する“実連携”: **Googleビジネスプロフィール（GBP）**
- 目標: **約1ヶ月**（目安: 2026-03-06）
- ロールは将来変わる可能性があるため、実装はロール名依存を避け **権限フラグ**中心で設計します（`docs/01_ROLES_PERMISSIONS.md`）。

## 現状（2026-02-03時点）
- 既存リポジトリは **Vite + React（フロント単体）**。
- データは `constants.ts` の固定モック + 一部 `localStorage`（ログイン/ツアー既読）で動作。
- 投稿/受信箱/設定/ユーザー管理は UIが揃っているが、永続化・外部API連携は未実装（ほぼモック）。
- Geminiによる投稿文生成はフロントから呼び出す形の実装がある（要APIキー）。

## ロール定義（暫定）
※ロールは“呼び名”が変わり得る前提。実装は権限フラグで行う。
- **ADMIN**: knomura（開発者/全権）
- **MANAGER**: TEPPEN MEOの営業/運用（USER権限 + ユーザー管理/配信など）
- **USER**: 店舗スタッフなど（基本機能）

## MVPスコープ（やる）
### 1) 認証・ユーザー・権限
- Supabase Authでログイン（メール/パスワード）
- 招待（invite）/パスワード再設定（reset）
- 画面の表示制御 + DB側（RLS）での拒否（“二段構え”）

### 2) マルチテナント（組織/店舗）と永続化
- 組織（Organization）/店舗（Store）/所属（Membership）を定義
- 主要データをDBに永続化（投稿/設定/連携/監査ログ）

### 3) 投稿運用（最小）
- 投稿の作成/編集/削除（下書き/予約/公開済み/失敗）
- 画像/動画のアップロード（Storage）
- 投稿一覧/カレンダーがDBデータで表示される

### 4) 統合受信箱（MVPはGBPのみ）
- GBPの口コミ（レビュー）取得
- 口コミへの返信送信
- 取得/返信の履歴をDBに保存

### 5) 管理・運用（最小）
- 連携状態の可視化（最終同期、エラー内容）
- 再同期ボタン
- 監査ログ（最低限: 連携設定変更、投稿作成/更新/削除、返信送信）

### 6) デプロイ
- 本番URLを用意（knomuraが迷わず触れる状態）
- 環境変数と秘密情報の整理（`docs/04_ENV_AND_SECRETS.md`）

## 非スコープ（MVPではやらない）
- Instagram / Facebook / TikTok の本格連携（審査・権限が重いので段階導入）
- MEO順位計測（Rank Tracker）
- Stripe課金/請求
- 高度な分析（インサイト統合/自動改善提案/自動最適化）
- “秘密情報を管理画面からGUIで登録”の本格対応（MVPでは環境変数運用を優先）

## Done定義（受け入れ条件）
- [ ] 実ユーザーがログインできる（招待/再設定が通る）
- [ ] ロール/権限で「できる/できない」がUIだけでなくDB（RLS）でも担保される
- [ ] 投稿（下書き/予約）とメディアがDB/Storageに保存される
- [ ] 投稿一覧とカレンダーがDBデータで動く（モック依存が外れる）
- [ ] GBP口コミを取得でき、返信できる（履歴が残る）
- [ ] 連携状態（最終同期/エラー）がGUIで確認でき、再同期できる
- [ ] 本番URLがあり、上記が再現できる（手順書に沿って確認できる）

## 既知のリスク / 注意点（対策）
- **OAuth（GBP）の設定は混乱しやすい**: knomura向け手順書を最優先で整備（`docs/05_RUNBOOK_KNOMURA.md`）。画面の接続ウィザード化も計画に含める。
- **RLSは難易度が高い**: “UIの制御”ではなく“DBで拒否”を正とし、ポリシーは最小から段階的に固める（`docs/02_DATA_MODEL_AND_RLS.md`）。
- **秘密情報の扱い**: クライアントにシークレットを置かない。MVPは環境変数で安全運用し、後続でGUI管理へ（`docs/04_ENV_AND_SECRETS.md`）。
- **定期同期/予約実行**: まずは“実行ログが残る”ところまでをMVPゴールにし、失敗理由が追えることを優先。
